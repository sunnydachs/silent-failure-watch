# silent-failure-watch

[English](README.md) | 日本語

無人で動くエージェントパイプラインにおける **偽の成功 (false success)** —
成果物もデータも実行も起きていないのに「完了」と報告する失敗 —
に関する記事シリーズの一次データリポジトリです。

2つのデータセットがあり、どちらも実際の単一マシンのエージェント運用
(WSL2ラップトップ上のcron駆動エージェント、実行1,000件、2026-10-24エクスポート)
で計測したものです。

1. `data/fleet_runs.jsonl` — 実cron実行1,000件の無害化エクスポート
   (ステータス・汎用ジョブ種別・エラー分類・実行時間・スケジュール遅刻)。
   `python3 scripts/analyze_fleet.py` で同じ集計が再現できます。
2. `experiments/inject/` — 小規模な制御グリッド: 4種類の環境故障を玩具タスクに
   注入し、エージェント自身の構造化ステータス報告と、ルールベースの状態検証器
   を突き合わせます。`python3 experiments/inject/run_grid.py` で再現できます。

外部の基準として arXiv:2606.09863 (「From Confident Closing to Silent Failure」、
tau2-bench 9,876軌跡 + AppWorld 1,879軌跡で偽の成功を計測) を引用します。
本リポジトリが付け足すのは、ベンチマークでは取れない2点です:
現実の運用fleetで無人失敗がどう見えるか、そしてエージェントの自己申告が
見落とすものを5行の状態チェックがどこまで捕まえるか。

## 構成

| パス | 内容 |
|---|---|
| `data/fleet_runs.jsonl` | 無害化済み実行レコード1,000件 (fleet数値の元データ) |
| `scripts/analyze_fleet.py` | エクスポートに対する分類・遅刻の集計 |
| `scripts/receipt_check.py` | レシートだけを見る偽成功チェッカー: 1実行の申告+叙述に対する決定論的ルール (S1-S3)。`--eval` でグリッドのground truthと突き合わせ |
| `scripts/export_fleet.py` | サイト固有のエクスポータ (非公開のcron DBを読む。マッピングファイルはコミットされない) |
| `scripts/job_type_map.example.json` | サイト固有マッピングの形式例 |
| `experiments/inject/run_grid.py` | 制御された偽成功グリッド |
| `tests/` | 分類器と報告パーサの単体テスト |
| `results/` | グリッドの生実行レコード。被験モデル2種ぶん (`inject_results.jsonl`、`inject_results_b.jsonl` — どちらのモデルも意図的に非記録、限界を参照) |

## 実行方法

```bash
# fleet集計 (標準ライブラリのみ)
python3 scripts/analyze_fleet.py

# 注入グリッド (任意のOpenAI互換エンドポイント)
export LLM_BASE_URL=...
export LLM_API_KEY=...
export LLM_MODEL=...      # 汎用チャットモデル
python3 experiments/inject/run_grid.py             # 5条件 x 8実行
python3 experiments/inject/run_grid.py --analyze    # 結果JSONLから集計

# テスト
python3 -m pytest tests/ -q

# レシートのみの偽成功チェック (標準ライブラリのみ・LLM不要・軌跡不要)
python3 scripts/receipt_check.py --eval             # フラグ vs グリッドのground truth
python3 scripts/receipt_check.py --eval tests/fixtures/receipt_cases.jsonl
echo '{"self_status": "success", "items_claimed": 0, "raw_tail": "wrote nothing"}' \
  | python3 scripts/receipt_check.py                # レシート1件をstdinでチェック
```

3つの評価は、主張が別物です (いずれもルールセットv2):

- **注入グリッド・モデルA (`results/inject_results.jsonl`、有効40件)**:
  偽成功8件をすべてフラグ、正常8実行で誤報0。このグリッドの偽成功は
  すべて `items_written: 0` なのに `status: "success"` と申告する
  空成功の形状で、全件がS1で捕捉、S2が「no items matched / catalog
  empty」の引用で裏付けます。
- **注入グリッド・モデルB (`results/inject_results_b.jsonl`、別モデル
  ファミリー。40試行・有効34件・ハーネスエラー6件除外)**: 偽成功7件を
  すべてフラグ、誤報0 — 同じ空成功の形状。両モデル合計では
  80試行・有効74件・偽成功15件・15/15捕捉・誤報0。15件はすべて
  同一の失敗形状 (空成功) で、S2の発火は同じ叙述の裏付けにすぎず、
  S2の一般性能の独立した証拠ではありません。
- **ラベル付き境界スイート (`tests/fixtures/receipt_cases.jsonl`、
  合成14件)**: 6件中5件捕捉、誤報0 — S2/S3をそれ自身の境界条件
  (未解決失敗の引用、処理済み一時失敗を引用した正当な成功、正直な
  部分報告) で測る唯一の評価。見逃し1件は文書化された天井です:
  失敗語彙の外で表現された疑念 ("assuming it landed") はレシート
  だけのチェックには見えません。

グリッドには思考量を制御できるチャットモデルが必要です。デフォルトで
思考が長いモデルは `max_tokens` を思考が食い潰して本文が1文字も出ないことが
あります (実測: 512トークン上限で思考570トークン・本文0、`finish_reason:
length`)。そのため `run_grid.py` は既定で低めの effort を送ります。
使用したモデルとパラメータは `results/` のトレースに記録されます。

## 先行研究との関係

現在存在する検知の系譜は、**1エピソードの内側・軌跡の上**で動くものです:

- arXiv:2511.04032 (2025-11) — エージェント軌跡の異常検知の最初の系統的研究
  (ドリフト・ループ・出力欠落): 整備された軌跡データセット (4,275+894) 上の
  XGBoost / SVDD。軌跡ストリーム全体とラベル付きデータが必要です。
- arXiv:2608.02464 (2026-08、`agent-trajectory-sentinel`) — ステップあたり
  約200µsのリアルタイム1クラス行動モニタ。異常検知にとどまらず、ツール
  結果から申告件数を再計算し必須呼び出しの実行を確認する決定論的検証器も
  構築しており、単純な完了チェックがsilent abortを捉えた結果も報告して
  いる。ステップ単位のテレメトリとツール結果が必要です。
- AgentTelemetry (ACM 2026) — エージェントオーケストレーション段階の
  spanレベル計装規約。計装されたspanが必要です。

本ツールの位置: これらのシステムは軌跡・ステップテレメトリ・ツール結果
から検証します。無人の定期ジョブには多くの場合、そのどれも計装されて
いません — 確実に存在するのは、実行ごとの簡潔なレシート (申告ステータス・
出力数・叙述テール) とスケジューラ自身の記録だけで、チェックはスケジューラ
の横で追加LLMなしに動く必要があります。本リポジトリは、その既存運用環境に
導入しやすいレシートのみの検査を実装・評価します。分野に検証ツールが
存在しないという主張ではありませんし、軌跡レベルの検知と競合せず補完
します。

## 正直な限界

- fleet実行1,000件は1台・1スケジューラでの事例研究です。エージェント運用全般
  の推定値ではありません。
- 注入グリッドは既知の注入を持つ玩具タスクです。エージェントの能力ではなく、
  故障時の自己申告の信頼性を測ります。
- グリッドの検証器はハーネスが制御する状態を読むため、自明に正しいです。
  それが要点 (安い状態チェックは自己申告に勝つ) ですが、検証器の列は
  デモンストレーションであってベンチマークスコアではありません。
- レシートチェッカーのグリッド結果 (2モデルで15/15捕捉・誤報0) は、
  空成功という1つの失敗形状の上に立っています。S2/S3はその形状の外の
  実モデルレシートでは一度も発火しておらず、その一般検知性能は合成の
  境界スイート (5/6、天井の見逃し1件) でしか測られていません —
  ルールレベルの実証であってモデルのベンチマークではありません。
- モデルBの実行では40試行中6件がハーネスレベルのエラーとして除外
  (チャットエンドポイントが再試行後に呼び出しを拒否 — レート制限)。
  ハーネスエラーとして記録され、どの分母にも入りません。
- 実運用での検知率は未測定です。このツールで実際の定期ジョブを検査した
  ことはまだありません。
- グリッドの被験モデルは意図的にどこにも記録していません (トレース含む)。
  任意のOpenAI互換チャットモデルで再実行して、自分のモデルを確かめてください。
